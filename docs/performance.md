# 性能

## 测试环境

- Windows / x86_64，20 逻辑核
- `cargo build --release`（`lto = "thin"`、`codegen-units = 1`、`panic = "abort"`）
- 两张输入：6 MP JPEG（3000×2000，117 KB）、45 MP 手机照片（8256×5504，22.3 MB）

## 6 MP：一切都很轻松

| 场景 | 结果 |
| --- | --- |
| 全分辨率解码 | **14.6 ms** 平均，约 410 MP/s |
| 解码到 256 px 缩略图 | 约 9 ms |
| 启动到显示第一张图 | 约 0.6 s（含按视口尺寸解码 3000×2000 → 2048×1365） |
| 二进制体积 | GUI 15.2 MB，CLI 3.7 MB |

Debug 构建下同样一张图约 18 ms —— 只比 release 慢一点点。这说明瓶颈在解码器本身，
而不是应用逻辑；也说明调优应该往解码器里找，而不是去优化事件循环。

## 45 MP：真正的体感在这里

手机照片的像素是上面那位的 7.5 倍，而且 **JPEG 解码是单线程**的，所以打开这样一张照片
要多久由解码器决定。按视口尺寸（2048 px）出预览，逐阶段实测：

| 阶段 | 优化前 | 优化后 |
| --- | --- | --- |
| 读文件（22.3 MB） | 7.5 ms | 7.5 ms |
| 探测尺寸 | 7.3 ms | 7.3 ms |
| JPEG 解码（全分辨率，单线程） | 245 ms | 245 ms |
| 转成 RGBA | 57 ms（全画幅 45 MP） | 3 ms（只转缩小后的 2.8 MP） |
| Lanczos3 缩放到 2048 | 68 ms（在 RGBA 上做） | 17 ms（在 RGB8 上做） |
| **合计** | **~397 ms** | **~281 ms** |

同一台机器上用 CLI 复现（含一次性的 rayon 线程池预热）：**447 ms → 276 ms**。
8.3 MP 的截图走同一条路：101 ms → 71 ms。

## 放大到 100%

预览是给「整张图都在视野里」用的；放大到 100% 要的是「一个图像像素对一个物理像素」，
于是后台换成全分辨率纹理。这里省下的是 UI 线程的卡顿和显存：

| 1280×800 窗口看那张 45 MP 照片 | 优化前 | 优化后 |
| --- | --- | --- |
| 上传的纹理 | 8256×5504 RGBA = **173 MB** | 可视区域约 2560×1536 = **15 MB** |
| UI 线程转换像素 | 42 ms | 约 4 ms |
| 平移时的补传 | 不需要（整张都在显存里） | 越过一屏才重传一次，约 4 ms |

顺带解决了一个隐患：显卡的最大纹理边（桌面 GPU 一般是 16384）以前是个硬上限，
比它大的全景图一放大就会在渲染后端 panic。现在上传的永远只是屏幕大小的一块。

## 复现

```powershell
cargo build --release

# 单张图解码 20 次
.\target\release\mapleview-cli.exe bench D:\photos\IMG_0001.jpg --runs 20

# 只看文件头，验证格式识别
.\target\release\mapleview-cli.exe info D:\photos\*.jpg --header-only

# 缩略图路径
.\target\release\mapleview-cli.exe thumb D:\photos\IMG_0001.jpg --size 256 --out t.png

# 换一张手机照片，看看预览路径要多久
.\target\release\mapleview-cli.exe thumb D:\photos\IMG_6420.jpg --size 2048 --out p.png
```

## 瓶颈在哪里

整条流水线是：

<div class="mx-flow">
  <span>读文件</span><i>→</i>
  <span>探测格式</span><i>→</i>
  <span>读文件头</span><i>→</i>
  <span>解码</span><i>→</i>
  <span>EXIF 旋转</span><i>→</i>
  <span>缩放</span><i>→</i>
  <span>RGBA</span>
</div>

在 6 MP 上，除了解码每一步都在微秒到亚毫秒量级。**在 45 MP 上这个说法不再成立**：
「转 RGBA」和「缩放」加起来占了整条流水线的三分之一。所以真正影响体感的是三件事：

1. **解码在哪个线程上发生** —— 在 UI 线程上就是卡顿
2. **解码出多少像素** —— 3000×2000 全解是 6 MP 的工作量，按视口只需要 2048×1365
3. **在多大的缓冲上做后处理** —— 缩放和转 RGBA 都是全画幅的逐像素操作，在 45 MP 的
   缓冲上做和在实际要显示的 2.8 MP 上做，差着一个数量级

枫阅的答案分别是「线程池 + 版本号取消」、「`DecodeHint` 指定目标尺寸」，以及
**先缩放、后转 RGBA**：JPEG 解出来是 RGB8，那就先在 RGB8 上把 45 MP 缩到 2.8 MP，
再转 RGBA。这一步不改变任何一个像素（有测试逐字节比对），却省掉了一次全画幅转换和
一份 173 MB 的中间缓冲。

解码本身仍然是下限：`image` 走的是纯 Rust 的 `zune-jpeg`，没有 libjpeg-turbo 那种
DCT 缩放解码（按 1/2、1/4、1/8 解）。换掉它能再砍掉相当一部分，代价是引入一个 C 依赖。

## 翻页与预取

- 当前图两侧各两张自动预取进缓存，按住方向键时不会每张都冷启
- 预取走**独立线程**，永远不会排在「用户正在等的那张」前面
- 每次导航**替换**预取队列而不是追加，否则一路连按会堆起一堆关于旧位置的猜测
- 翻回看过的图是零解码：缓存按字节计费，命中即贴图
